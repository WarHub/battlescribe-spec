# Adapter protocol v1.2 — native artifacts in, native artifacts + annotations out

Status: approved design, pre-implementation.
Issue: [#298](https://github.com/WarHub/battlescribe-spec/issues/298) (part of epic #73).
Related: reframes the output-side of #270 (adapter de-duplication) and its
subtasks #282/#283/#284; shares surface with #279 (roster file lifecycle);
builds on the unified-CLI adapter protocol (v1.1) in #271 /
[2026-07-07-unified-cli-design.md](./2026-07-07-unified-cli-design.md). Wire-type
edits are governed by the `changing-protocol-types` skill.

## Goal

Stop making adapters *translate* the data model in both directions. Today each
adapter builds its native model from structured protocol DTOs on the way in, and
builds a normalized `RosterState`/`ValidationErrorState` DTO tree from its native
model on the way out. Both are per-engine translation code.

v1.2 flips the contract: the adapter **loads a native data artifact** on the way
in and **emits a native roster artifact plus a thin runtime-annotations sidecar**
on the way out. All neutral-model ↔ native-format conversion and all state
reading/evaluation move to the **runner**. Adapters get thinner; the reference engine
gains fidelity (it loads game data through its real XML path); and the wire is
ready to carry non-XML native formats for future engines.

### Drivers (in priority order)

1. **Adapter simplicity** — adapters load an artifact and expose behavior; no
   model-building or DTO-tree construction.
2. **Higher fidelity** — engines load data via their real app path (the
   BattleScribe reference engine parses generated `.gst`/`.cat` through
   `DataUtils`/SimpleXML, like the desktop app, instead of a synthetic
   programmatic build).
3. **Future formats / engines** — the wire carries a format-tagged native
   artifact; onboarding a JSON-native engine adds one serializer, not a bespoke
   DTO mapping.

Non-goal: "kill the input inconsistency between engines" is a welcome side effect
(both engines end up loading the same generated bytes) but is not a design driver.

## Scope

**In.** Two coordinated changes shipped together as one v1.2 protocol overhaul:

- **B — format-negotiated setup.** Setup data crosses the wire as native files
  with a format tag, generated on the runner.
- **C1 — combined `getState` (export + runtime-annotations).** Roster state is
  read on the runner by parsing the native export and overlaying a small
  annotations sidecar; errors ride the same `getState` result, node-linked by uid.

**Out.**

- Actions (`addForce`, `selectEntry`, …) stay behavioral and ID-addressed — they
  are commands, not data, and do not become artifacts.
- `screenshot` / record commands are unchanged.
- Spec YAML authoring surface is **unchanged** — this is purely an internal
  protocol/runner refactor. `expectedState` and `expectedFile` keep their
  meaning.

## Why the boundary sits here (surface analysis)

Every protocol surface was checked against "could this become a native artifact
the adapter just loads/emits, instead of a DTO it translates?"

| Surface | Dir | Adapter does today | Becomes a native artifact? |
|---|---|---|---|
| Setup (normal) | in | builds model from DTOs (BS programmatic; NR DTO→XML) | **Yes — B** |
| Setup (dataSource) | in | loads raw `.gst`/`.cat` | already native; folded into B |
| Action | in | behavioral op | No — a command, not data |
| exportRosterXml | out | native serialize | already native; folded into C1 |
| screenshot | out | native PNG | already native; untouched |
| GetState | out | builds `RosterState` from native model | **Partially — C1** (see below) |
| GetErrors | out | builds `ValidationErrorState[]` | No — errors aren't in a roster file; they are computed |
| describe | meta | capability handshake | stays; carries format negotiation |

The output side is mostly already native (export, screenshot) or genuinely needs
adapter computation (errors don't exist in a roster file). So the meaningful move
is the **input** side plus the **structural** part of state.

### What state/errors contain that the exported roster does *not*

Diffed against a real exported `.ros` (the `protocol-kitchen-sink` snapshot).
Most of `RosterState` is in the file or derivable from it: forces, selections,
costs, profiles, rules, categories, `customName`/`customNotes`, `page`, `type`,
`number`, `entryGroupId`, `entryId`, publications; `publicationName` resolves from
the force-level `<publications>` id→name block; profile/rule `hidden` is written
(`hidden="false"`).

Only three things are genuinely file-absent:

1. **Validation errors** — a roster file never stores validation state.
2. **`hidden` on forces/selections** — written on `<rule>`/`<profile>` but not on
   `<force>`/`<selection>`; that flavor is resolved from entry + modifiers at
   runtime (`GetResolvedEntry().isHidden()`). (Categories have no `hidden` field
   in `CategoryState`, so no concern there.)
3. **`availableEntryCount`** (root-force level) — an engine/UI count, never
   serialized.

**Ordering is not a file-absent concern — it is a deliberate non-goal.** The
`.ros` serializes forces/selections in engine/data order; today the BattleScribe
adapter fabricates a *display* order via `RosterNameNodeComparator` (name
case-insensitive) that is not in the file. A serialization-conformance suite must
test **the order the app writes to disk**, not its display sort (which is a
presentation concern and may be a user-configurable in-app setting). So the
adapter's UI-sort is **deleted**, and force/selection assertions conform to
document order in the export. This is why the annotations sidecar (below) carries
only runtime-derived *semantics*, never presentation ordering.

## Design

### 1. Setup (B) — format-negotiated files

- The runner keeps the neutral authoring model — the spec's `ProtocolGameSystem`
  / `ProtocolCatalogue` from `SpecLoader.GetSetupData`.
- New **serializer registry** on the runner mapping format id → serializer.
  Initial entry: `battlescribe-xml → CatXmlGenerator` (lifted out of
  `NewRecruitRosterEngine`, where it currently runs adapter-side). This registry
  is the sole extension point for future formats (`bsdata-json`, …).
- `describe` result gains `acceptedSetupFormats: string[]`. The runner picks the
  best format both it and the engine support, serializes the neutral model to
  files, and sends **one** setup command:
  ```
  SetupCommand {
    specId,
    format:  string,                    // e.g. "battlescribe-xml"
    files:   { fileName, content }[]    // .gst + N .cat today
  }
  ```
- `dataSource` specs use the **same** command with the real files and
  `format: "battlescribe-xml"` — no serialization step. The two old setup paths
  (`setup` with DTOs + `setupFromFiles`) collapse into this one.
- Adapters implement a single `SetupFromFiles(format, files)`:
  - **BattleScribe reference**: loads the files via `DataUtils`/SimpleXML
    (`LoadGameSystemFile` + `LoadCatalogueWithDependencies`) — the real app load
    path. `SetupFromProtocol` and the `JavaModelFactory` programmatic build are
    deleted.
  - **NewRecruit** (both drivers): loads the wire-delivered XML via
    `loadSystemFromFs`; the adapter no longer calls `CatXmlGenerator`.

### 2. `getState` (C1) — one combined output command

The `getState` command is **repurposed**: instead of returning a built
`RosterState`, it returns the whole roster read in one atomic message, absorbing
the old separate `getErrors` and `exportRosterXml` at assertion points. (Reusing
the familiar verb — "snapshot" is avoided because it already names the `bs-spec
snapshot` verb (#276) and the `expectedFile` snapshot files.)

```
StateResult {
  files:       { fileName, content }[]                  // native roster export (.ros today)
  annotations: { uid, hidden?, availableEntryCount? }[] // runtime-derived semantics; NO ordering
  errors:      ValidationErrorState[]                   // unchanged shape
}
```

- **`files`** — the native roster export, exactly what `exportRosterXml` produces
  today (BattleScribe's `DataUtils` serializer for the BS engines; NewRecruit's
  `exportRos` for the NR engines). `expectedFile` byte-compares this verbatim;
  the existing `.ros` snapshots are unchanged. This is the sole source of
  structure and ordering — see §7 (adapter output).
- **`annotations`** — only the **runtime-derived semantics** absent from
  serialization: `hidden` on forces/selections and `availableEntryCount` on root
  forces, keyed by the instance **uid** (which the export stamps as the `id`
  attribute on every `<force>`/`<selection>` — the same uids actions return).
  Deliberately carries **no ordering** — presentation order is not conformed
  (see the surface analysis). Unordered set; the runner overlays each entry onto
  the parsed node with the matching uid. (Optimization for the plan: omit
  `hidden` when false to keep the payload small.)
- **`errors`** — the same `ValidationErrorState[]` adapters compute today. This
  channel is essentially unchanged.

### 3. Runner-side evaluation (parse once, no re-materialization)

Assertions evaluate **directly against the parsed export** — the runner does not
rebuild a normalized `RosterState` object graph per `getState` just to read a
handful of asserted fields. A shared `StateView`, used by **both** the
in-process path (`RosterRunner`) and the out-of-process path
(`JsonProtocolEngine` over NDJSON):

1. Parse `files` **once** into a queryable typed model using the vendored
   **WHAM `WarHub.ArmouryModel`** roster reader. One parser serves both engines
   because both export the roster schema (`.ros`). Force/selection order is the
   document order — no sort.
2. Overlay annotations by uid: `hidden` / `availableEntryCount` are read from the
   sidecar for the node with the matching uid; every other field is read from the
   parsed node.
3. Expose `errors` as-is.

The `expectedState` evaluator (`AssertState`/`AssertForce`/…) is retargeted from
`RosterState` to `StateView`. Positional force/selection comparison
(`RosterRunner.cs:519,784`) now runs against serialization order; keyed
collections (costs/profiles/rules/categories) are unaffected. `RosterState`
survives only as an **optional projection** built on demand for tooling that
needs a serializable normalized snapshot (the differential runner #274, CLI
display) — never on the assertion path, so nothing is remapped twice.

### 4. Errors — association by uid

The errors channel carries `ValidationErrorState (Message, OwnerType,
OwnerEntryId, EntryId, ConstraintId, RaisedOnType, RaisedOnId)` unchanged.
Assertions (`ErrorAssertionDef` "on"/"from") match on `OwnerType`/`OwnerEntryId`/
`EntryId`/`ConstraintId` as today. Association to parsed nodes in the `StateView`:

- **force / selection owner** → `RaisedOnId` = instance uid → direct join to the
  parsed node's `id`. Precise even with duplicate entries (uid is unique).
  (Written as `OwnerId` when this design was drafted; #421 split that field's two
  meanings apart and the instance uid is the raisedOn half. Note the join is only
  available where the engine populates it — both BattleScribe lanes do, NR does
  not yet, #422.)
- **roster / cost-limit owner** → reserved pseudo-addresses (`"roster"`,
  `"costLimits/{costTypeId}"`), already how `ErrorAssertionDef.From` works.
- **category owner** → composite `(parent uid + category entryId)`, because
  category `id`s in the export are engine-random, not stable step outputs.
- **definition-level cause** → `EntryId` + `ConstraintId` (unchanged).

Errors never enter the file; they are a parallel channel joined by a precise,
per-run-stable handle present on both sides.

### 5. Interface and wiring changes

- **`IRosterEngine`**: remove `Setup(ProtocolGameSystem, ProtocolCatalogue[])`,
  `GetRosterState()`, `GetValidationErrors()`, and `ExportRosterXml()`. Add
  `SetupFromFiles(string format, IReadOnlyList<(string,string)> files)` and
  `StateResult GetState()` (the same DTO the wire carries — the in-process engine
  hands it straight to the runner). Adapters lose `SetupFromProtocol` /
  `JavaModelFactory` (BS) and the recursive `CaptureForce`/`CaptureSelection`
  DTO-tree builders (all engines) — they emit the flat annotations map instead.
- **Protocol messages**: `SetupCommand` gains `format` + `files` (DTO fields
  removed). `GetStateCommand` is **repurposed** (no params; returns the combined
  read). Removed commands: `SetupFromFilesCommand`, `GetErrorsCommand`,
  `ExportRosterXmlCommand`. `StateResponse` is replaced by `StateResult`
  (`"stateResult"`) with `{files, annotations, errors}`; `ErrorsResponse` and
  `RosterXmlResult` removed. Register `StateResult` in the `[JsonDerivedType]`
  tables and `ProtocolJsonContext`. `SetupResult` (setup still returns init
  errors) and the `screenshot`/record commands are untouched.
- **`ServeCommand`**: drop the `RosterXml = name is "battlescribe-ui"` gating —
  all four engines already implement export, so all support `getState`.
  `RosterXmlExporter`/`ScreenshotProvider` wiring is replaced by a single
  state provider.
- **`describe`**: `acceptedSetupFormats` added; protocol version → `1.2`.

### 6. Back-compat — hard-cut

All adapters are in-repo, so there is no mixed-version interop to preserve. v1.1
setup/state/errors/export commands and their DTOs are **deleted**, not
deprecated. `describe` advertises `1.2`; a `1.1` handshake is a hard error.

### 7. Adapter output is the adapter's call

An adapter emits whatever native artifact it decides to; the runner treats
`files` as **opaque bytes and has no fixup concept or registry**. Normally that
is the engine's verbatim export. But an adapter may adjust its raw output before
sending — BattleScribe is deeply legacy and may emit run-to-run nondeterminism or
a custom addition that isn't part of the data contract. That adjustment lives
entirely in adapter code and is the adapter's decision; the runner neither knows
nor cares.

What we keep is a **repo-internal development convention, not a protocol
feature**: for our in-repo adapters, any such fixup must be explicitly justified
and approved in review (and documented), so divergence from real app output is a
deliberate, visible choice rather than silent drift. It is a code-review norm
enforced by people, not runner machinery — and it does not bind third-party
adapters, whose output is simply their own.

Optionally, an adapter MAY **declare applied fixups on the wire** — an
`appliedFixups?: string[]` on the result is a cheap diagnostic that surfaces the
delta in run output. Not required; the runner only records/displays it.

`expectedFile` therefore compares exactly what the adapter sent (**post-fixup**) —
there is no "raw vs adjusted" distinction at the protocol level, because the
adapter's output *is* the artifact.

## Assertion semantics

- `expectedFile` = byte-compare the `files` on the wire (whatever the adapter
  sent; still run through `TemplatizeRosterInstanceIds`). Existing `.ros`
  snapshots unchanged except where an adapter fixup changes the bytes.
- `expectedState` = evaluate against the `StateView` (parsed export +
  annotations overlay + errors). Force/selection order is **serialization order**.
- **Migration (one-time):** `expectedState` snapshots and hand-authored
  force/selection sequences that currently assume the fabricated UI (name) order
  are regenerated/re-authored to serialization order. Keyed collections
  (costs/profiles/rules/categories) are unaffected. No YAML *schema* change — only
  the ordering of positional list assertions where it differed from wire order.

## Testing strategy

- The existing conformance suites are the regression oracle: every
  `expectedState`, `expectedFile`, and error spec must produce identical results
  before and after, across all four engines.
- `protocol-kitchen-sink` + the protocol serialization tests (renamed to 1.2)
  exercise the new wire types round-trip.
- New focused tests: serializer-registry format selection; `StateView`
  (WHAM parse → annotation overlay → error association) against fixed export
  fixtures; uid/pseudo-address error association including duplicates and category
  owners; export-fixup application + run-recording.

## Implementation order (single branch)

1. **Fidelity audits (gate before deleting anything):**
   - `CatXmlGenerator` vs `JavaModelFactory` coverage — can every setup construct
     a spec uses be expressed as `.gst`/`.cat` the reference engine loads? This
     is the top risk: today BS bypasses `CatXmlGenerator`.
   - WHAM roster-parse round-trip — does it recover everything `expectedState`
     asserts, against the current snapshots?
2. Protocol types: reshape `SetupCommand`; repurpose `GetStateCommand`; add
   `StateResult`; remove legacy (per `changing-protocol-types`).
3. Runner: serializer registry + `StateView`; retarget the `expectedState`
   evaluator from `RosterState` to `StateView`; `RosterRunner` and
   `JsonProtocolEngine` switch to `SetupFromFiles`/`GetState`.
4. Adapters: rewrite the four engines to the new interface; delete DTO builders,
   the UI-sort comparator, `SetupFromProtocol`, `JavaModelFactory`, adapter-side
   `CatXmlGenerator`. No fixups yet — they are added later, one at a time, only
   when a concrete legacy/nondeterminism case forces it (§7).
5. Migrate `expectedState` snapshots/assertions from UI order to serialization
   order.
6. Host: `ServeCommand`/`HostEngineFactory` wiring; drop export gating.
7. Delete dead code; run full conformance parity.

## Risks

- **`CatXmlGenerator` becomes load-bearing for the reference engine.** If it can't
  express something a spec's setup uses, BS setup breaks. Mitigation: audit is
  step 1; keep `JavaModelFactory` until the audit and full conformance pass.
- **WHAM roster-parse fidelity.** Must recover everything `expectedState` asserts
  (structural fields). Mitigation: fixture tests before removing the adapter DTO
  builders.
- **Ordering migration.** Switching force/selection assertions from fabricated UI
  order to serialization order changes existing snapshots/assertions. Mitigation:
  it is a mechanical, reviewable sweep (step 5) and the diff makes any surprising
  serialization order visible — which is itself worth knowing.
- **Fixup creep.** The adapter's freedom to adjust output could erode fidelity if
  fixups proliferate. Mitigation is a repo review convention, not runner machinery
  (§7): each fixup is justified/approved in review, optionally declared on the
  wire, and held to an "assert as-is if possible" bar.
- **UI-driver export cost.** `getState` now always exports (drives NR's export UI
  / the BS Java agent) on every `expectedState` step, not only `expectedFile`
  steps. Measure; if hot, cache the export per unchanged roster revision.
